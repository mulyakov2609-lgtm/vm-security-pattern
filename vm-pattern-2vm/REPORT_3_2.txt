3.2. Развёртывание микросервисов

Для развёртывания прототипа паттерна безопасности предусматривается использование двух виртуальных машин под управлением Ubuntu, созданных в Oracle VirtualBox. Первая виртуальная машина ВМ1 используется в качестве тестового клиента, имитирующего обращения со стороны потенциального нарушителя. Вторая виртуальная машина ВМ2 предназначена для размещения защищаемого приложения и микросервисов безопасности.

В отличие от трёхмашинной конфигурации, средства защиты и прикладные компоненты размещаются на одной защищаемой виртуальной машине, но выполняются в отдельных контейнерах. Контейнеризация применяется для раздельного запуска приложений и сервисов [3]. Управление контейнерными компонентами организуется средствами Kubernetes [1].

ВМ1 и ВМ2 подключаются к внутренней сети VirtualBox lab-net. Для стенда предусматриваются адреса 192.168.50.10/24 у ВМ1 и 192.168.50.20/24 у ВМ2. Дополнительные адаптеры NAT используются для установки программ и загрузки образов. Мостовое подключение лабораторной сети к внешней сети не предусматривается. Общие папки, общий буфер обмена и Drag-and-Drop отключаются в настройках гипервизора, если они не требуются для работы стенда. Код прототипа не управляет этими настройками автоматически.

На ВМ2 устанавливаются Docker Engine, minikube и средства управления кластером. Для графического просмотра ресурсов используется Lens. ВМ1 для текущего этапа не требует установки Docker или Kubernetes: она обращается к опубликованной точке входа приложения.

Для сборки компонентов применяется общий образ vm-pattern:3.0. В его состав входят файл app.py и фиксированный демонстрационный файл /protected/demo.txt. Каждый микросервис использует тот же образ, но запускается в отдельном поде с собственной ролью, задаваемой переменной окружения ROLE.

Состав ролей: gateway — сетевой шлюз; api — обработка прикладных запросов; data — защищаемый ресурс; security — проверка файловой политики; audit — регистрация событий. Все пять компонентов размещаются в Kubernetes на ВМ2. Внешний адрес PROTECTED_APP_URL больше не используется: API-сервис обращается к data по внутреннему адресу http://data:8000.

Ниже приведена конфигурация сборки образа.

Листинг — Dockerfile микросервисов

```dockerfile
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
COPY app.py /app/app.py
RUN mkdir /protected && echo "Protected demonstration file on VM2" > /protected/demo.txt && chmod 444 /protected/demo.txt
USER 10001:10001
EXPOSE 8000
CMD ["python", "app.py"]
```

Контейнерные процессы запускаются от пользователя с идентификатором 10001. Файловая система и привилегии дополнительно ограничиваются конфигурацией Kubernetes. Каталоги других виртуальных машин и сокет Docker внутрь подов не подключаются.

Для запуска локального кластера на ВМ2 используется Docker-драйвер minikube и сетевой плагин Calico. Выбор сетевого плагина связан с дальнейшим применением NetworkPolicy. Кластеру присваивается имя vm-lab.

```bash
minikube start -p vm-lab --driver=docker --cni=calico --cpus=2 --memory=4096
```

Сборка и загрузка образа выполняются командами:

```bash
docker build -t vm-pattern:3.0 .
minikube -p vm-lab image load vm-pattern:3.0
```

Манифест k8s.yaml описывает namespace secure-app, пять Deployment, пять внутренних Service типа ClusterIP и сетевые политики. Для каждой роли предусматривается одна реплика. Во время устойчивой работы ожидается наличие пяти подов с готовыми контейнерами. При обновлении Deployment временно могут существовать дополнительные экземпляры, поэтому снимок делается после завершения обновления.

Служебный токен создаётся на ВМ2 в файле .env и передаётся подам через Secret internal-token с ключом INTERNAL_TOKEN. ВМ1 не получает этот токен. Его значение не включается в исходный манифест, отчёт или снимки экрана. Единый токен является упрощением учебной реализации и не заменяет сетевое разграничение и защищённый транспорт.

Для подов задаётся запуск от непривилегированного пользователя и стандартный профиль seccomp. Контейнеры используют корневую файловую систему только для чтения, не могут повышать привилегии и не получают дополнительных Linux capabilities.

Листинг — Основные параметры безопасности контейнера

```yaml
securityContext:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop:
      - ALL
```

Для контроля готовности используется HTTP-обработчик /health. Положительный ответ подтверждает готовность соответствующего процесса к приёму запросов, но не проверяет автоматически весь маршрут gateway → api → data.

Базовая NetworkPolicy предусматривает запрет входящего и исходящего трафика подов. Дополнительные политики разрешают только предусмотренные направления: gateway → api и audit; api → data, security и audit. Для компонентов, обращающихся к внутренним именам сервисов, разрешаются DNS-запросы. Обращения gateway непосредственно к data не включены в разрешения. Фактическое применение ограничений проверяется отдельно после запуска.

Использование контролируемого маршрута к защищаемому ресурсу соответствует подходу к разграничению доступа на основе контроля виртуальных соединений [7]. Конкретные правила Kubernetes являются проектными решениями настоящей работы и не приписываются указанному источнику.

Применение манифеста и просмотр подов выполняются командами:

```bash
kubectl apply -f k8s.yaml
kubectl -n secure-app get pods
```

Для временного учебного доступа со стороны ВМ1 на ВМ2 открывается отдельная сессия перенаправления порта:

```bash
kubectl -n secure-app port-forward --address 127.0.0.1,192.168.50.20 service/gateway 8080:8000
```

Шлюз становится доступен по адресу http://192.168.50.20:8080. Остальные сервисы напрямую на интерфейсе ВМ2 не публикуются. Сессия должна оставаться активной; при её завершении или смене выбранного пода доступ организуется повторно.

Port-forward используется только как временный способ доступа к учебному приложению, а не полноценный production ingress. Этот маршрут может не сохранять исходный IP клиента в приложении. Поэтому в текущей реализации используется общий лимит шлюза — пять запросов за десять секунд для одной реплики, а не индивидуальное ограничение по адресу ВМ1. Также путь port-forward не рассматривается как проверка обычных ingress-правил NetworkPolicy. Для расширенной оценки внешнего доступа потребуется отдельная конфигурация ingress и доверенного определения источника.

Для получения снимка графического списка Lens подключается к кластеру vm-lab через локальный kubeconfig. В разделе Workloads → Pods выбирается namespace secure-app. После фактического запуска в отчёт включается собственное изображение пяти готовых подов.

Развёртывание создаёт основу для последующей проверки паттерна, но само наличие запущенных подов не доказывает предотвращение всех межвиртуальных воздействий или защиту гипервизора от эксплуатации уязвимостей.

Исправления в подразделе 3.1

Заменить описание распределения компонентов следующим абзацем:

«Прототип включает пять микросервисов: gateway, api, data, security и audit. Все компоненты запускаются в отдельных подах Kubernetes на защищаемой ВМ2. ВМ1 используется только для формирования тестовых обращений. API-сервис получает демонстрационные данные через внутренний Service data; отдельный внешний адрес сервиса данных не используется».

В листинге обращения к данным использовать:

```python
return call("data", "/data")
```

После положительной проверки файловой политики использовать:

```python
return call("data", "/file")
```

Удалить PROTECTED_APP_URL и call_data из старого трёхмашинного описания. Полная функция get_data остаётся в сервисе data. Для соответствия текущему способу доступа заменить формулировки индивидуальной блокировки источника по IP на описание общего лимита gateway. Если в схеме главы 2 есть отдельная ВМ3, привести её в соответствие: приложение и Kubernetes находятся на ВМ2, ВМ3 отсутствует.
